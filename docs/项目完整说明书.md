# 一、 需求拆解与业务闭环

### 1.1 业务背景与企业痛点
在传统的 B2B 客户邮件沟通与线索跟进中，企业普遍存在三大断裂点：
1. **响应时效慢与商机蒸发**：跨时区沟通首呼时效长达 12~24 小时，错过客户决策黄金窗口；
2. **跟进断层与机械打扰**：销售在初次报价后缺乏系统化跟进机制，或跟进邮件千篇一律引起客户反感，更有甚者在客户已回信后依然误发跟进（撞车事故）；
3. **画像缺失导致沟通生硬**：缺乏长期客户偏好沉淀，每次回信均从零开始，无法展现定制化服务能力。

### 1.2 核心业务流程与六步闭环拓扑
系统采用事件驱动与状态机协同架构，形成端到端闭环：

```
[外部邮件到达]
     │
     ▼
【1. 监听接入与脱水预处理】
  - Webhook / Graph API 监听
  - 附件与富文本 HTML 剥离落入 S3，Graph 内仅存精简上下文
     │
     ▼
【2. 结构化 Triage 与微观意图栈】
  - Pydantic Schema 强类型抽取：类别、紧急度、情绪、微观意图优先级栈
     │
     ▼
【3. 宏观阶段判定与画像加载】
  - SalesGPT 阶段机判定（破冰 ➔ 审查 ➔ 价值 ➔ 异议 ➔ 促成）
  - 从长期 Store 毫秒级召回客户画像快照（只读透传）
     │
     ▼
【4. 动态分支生成决策】
  - 画像完备 ➔ 深度个性化方案生成
  - 画像不足 + 高意图 ➔ 价值置换混合探针（解答 + EVOI 最优探针）
  - 画像不足 + 弱意图 ➔ 标准通用模块化回复
     │
     ▼
【5. 轻量流式质检与 HITL 梯度放量】
  - 20ms 流式三级实体命名空间核验，拦截越权承诺
  - 梯度放量（Level 0 强审批 / Level 1 180s 撤回直发 / Level 2 静默直发）
     │
     ▼
【6. 延时跟进防撞车闭环】
  - 注册延时任务 ➔ 出站前 1ms 原子条件排他围栏 ➔ 动态二次触达/结案
```

### 1.3 宏观阶段与微观意图双轨解耦
为彻底解决长邮件中多意图交织导致状态机“车轱辘话”震荡的问题，系统推行双轨架构：
- **宏观生命周期阶段（Macro-State）**：追踪商机阶段，具备滞后单调性。仅在发生关键里程碑时前进，回退需人工或守卫校验；
- **微观意图栈（Micro-Action Stack）**：
  $$\text{Priority: } \text{Scheduling (日程邀约)} > \text{Objection (异议阻断)} > \text{Inquiry (需求审查)} > \text{General}$$
  单封邮件包含多个诉求时，按优先级分别调用 Sub-Skill 检索，由 Synthesizer 合并成一封结构严密的完整回复。

### 1.4 人机协同 (HITL) 动态信任分流模型
构建综合信任度准入得分公式：
$$S = w_1 C_{\text{intent}} + w_2 (1 - D_{\text{levenshtein\_roll}}) + w_3 C_{\text{rag}} - P_{\text{risk}}$$
- **Level 0（强制阻塞审批，Score < 0.6 或命中硬红线）**：飞书/企微推送卡片，人工审核确认；
- **Level 1（180秒反悔直发，0.6 ≤ Score < 0.85）**：生成后向业务员推送倒计时卡片，3 分钟内可一键拦截，无操作则自动投递。将同步阻塞变为异步旁路纠错；
- **Level 2（静默自动直发，Score ≥ 0.85 且长尾标品）**：直接投递，异步记录审计日志；
- **熔断控制**：最近 50 封邮件中拦截率 $> 15\%$ 时，该业务线自动降级回 Level 0。

# 二、 LangGraph 核心状态设计与并发架构

### 2.1 状态契约分层定义 (State Schema)
```python
from typing import Annotated, List, Optional, Literal, Dict, Any
from typing_extensions import TypedDict
from pydantic import BaseModel, Field
from langgraph.graph.message import add_messages

def replace_channel(old_val, new_val):
    """瞬态信道覆写 Reducer，不沿轮次累积"""
    return new_val

class EmailAgentState(TypedDict):
    # 1. 通信消息信道（脱水后的消息序列）
    messages: Annotated[List[Dict[str, Any]], add_messages]

    # 2. 会话隔离与路由标识
    tenant_id: str
    thread_id: str
    sender_email: str
    company_domain: str

    # 3. 客户画像与业务阶段
    customer_profile: Dict[str, Any]
    macro_sales_stage: Literal["icebreak", "qualification", "value_prop", "objection_handling", "closing"]
    micro_intent_stack: List[str]

    # 4. 计数器与门禁
    clarification_count: int
    triage_confidence: float

    # 5. 瞬态工作信道（单轮覆写，不入持久化累加）
    rag_context_refs: Annotated[List[str], replace_channel]
    critic_scratchpad: Annotated[Optional[Dict[str, Any]], replace_channel]
    current_draft: Annotated[Optional[str], replace_channel]
    hitl_level: Annotated[int, replace_channel]
```

### 2.2 动静分离与 Checkpointer 状态防膨胀治理
- **瞬态信道分离**：RAG 切片引用与 Critic 思考过程采用 `replace_channel`，单轮覆写，禁止沿轮次累积；
- **Blob 外部化引用 (Offloading)**：富文本 HTML 与大附件在入口上传 S3/MinIO，Graph 仅存精简文本与 `s3://` URI，单个 Checkpoint 压缩在 $50\text{KB}$ 以内，彻底避免 PostgreSQL TOAST 膨胀；
- **Compaction 剪枝节点**：当对话轮次超过阈值时，自动调用 `RemoveMessage` 剪除中间旧节点，并以一条 `[历史邮件摘要]` SystemMessage 替代；
- **检查点 GC**：仅保留会话回合终态的 Final Checkpoint，中间 Node 快照自动清理，WAL 日志写入量降低 80%。

### 2.3 双层物理隔离机制（防丢与防串线）
```
                 ┌─────────────────────────────────────────┐
                 │       请求入口: thread_id, sender       │
                 └────────────────────┬────────────────────┘
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
┌─────────────────────────────────┐       ┌─────────────────────────────────┐
│     Level 1: 线程短期运行态     │       │     Level 2: 客户长期画像态     │
│      (LangGraph Checkpointer)   │       │       (LangGraph Store / DB)    │
├─────────────────────────────────┤       ├─────────────────────────────────┤
│ • 作用域：严格按 thread_id 隔离 │       │ • 复合命名空间 (Namespace)：    │
│ • 保证：并发邮件间内存物理隔离  │       │   (tenant_id, "profiles", domain)│
│ • 存储：当前对话链状态与断点    │       │ • Key：标准化 sender_email      │
└─────────────────────────────────┘       └────────────────┬────────────────┘
                                                           │ (只读快照加载)
                                                           ▼
                                          ┌─────────────────────────────────┐
                                          │  state["customer_profile"] 只读 │
                                          └─────────────────────────────────┘
```

### 2.4 事务性外箱 (Outbox) 与长期记忆一致性保障
- **执行期本地覆盖视图 (Overlay View)**：线程内执行时只读加载 Store，本轮提取的增量暂存本地 `local_profile_delta`，不加跨线程行锁；
- **事务外箱 (Transactional Outbox)**：节点执行中严禁直接调 `store.put()`。当整图到达成功终态时，原子写入 `outbox_events` 表；
- **单键串行化分区**：MQ 以 `hash(tenant_id + domain + email)` 为 Partition Key，保证同客户画像单线程顺序消费；
- **CAS 乐观锁**：带 ETag 版本号写入，冲突时触发指数退避与语义级补丁合并。

# 三、 幻觉防控与安全护栏架构

### 3.1 证据强溯源：双层锚定与 NLI 蕴含门禁
为兼顾高精确度与口语化高召回，采用**“双层锚定范式（Span-Offset + NLI 拓扑对齐）”**：
1. **三阶弹性 Span 匹配器**：
   - Tier-0：严格子串命中；
   - Tier-1：Unicode/NFKC 规范化对齐（处理标点、全半角、空格）；
   - Tier-2：变长滑动窗口 Damerau-Levenshtein 容错（相似度 $\ge 0.88$ 时反向吸附为原文确切切片 `raw_email[start:end]`）；
2. **声明-证据解耦与 NLI 蕴含门禁**：
   - Pydantic 模型拆解为 `evidence_span`（原文字符切片）与 `normalized_fact`（规范化事实）；
   - 本地轻量 Cross-Encoder 执行断言：当且仅当 $\mathcal{P}(\text{Entailment}) \ge 0.92$ 时接收事实，无法蕴含时打标 `DEGRADED_UNVERIFIABLE`，平滑回退，坚决不向生成侧透传伪造事实。

### 3.2 间接提示词注入与长期记忆防投毒规范
1. **三权分立隔离架构（Reader-Arbiter-Writer）**：
   - **Reader Agent**：在无外部工具权限沙箱中只读运行，仅提取受限 JSON；
   - **Arbiter（确定性 Python 规则引擎）**：价格、折扣、合同权限由 Python 微服务校验（`assert discount <= 0.2`），剥夺 LLM 商业裁决权；
2. **长期记忆类型化与非自然语言存储**：
   - 硬事实强制转换为 Enum/数值 Schema，注入指令因类型不符被丢弃；
   - 软风格仅提炼为浮点特征向量（如 `formality: 0.85`），绝不回写自然语言文本；
3. **Canary 令牌动态熔断**：System Prompt 注入高熵 Canary Token，出站流量实时监测，一旦泄露毫秒级熔断挂起。

### 3.3 轻量流式 Critic 质检与三级实体命名空间
- **流式轻量提取**：废除二次大模型审查，采用 Rust `FlashText` + 本地 `GLiNER`，耗时 $< 20\text{ms}$；
- **三级实体命名空间分流**：
  - **Namespace A（高危商业承诺：价格/SLA/交期）**：底表倒排索引强校验；
  - **Namespace B（公开技术术语：AWS/K8s/Python）**：本地静态 Trie 树白名单直接放行；
  - **Namespace C（常识/礼貌用语/相对时间）**：划入忽略集；
- **原地修剪替换与单次熔断**：未锚定商业断言原地替换为安全占位符，重试预算限制为 1 次，超限直入人工复核。

# 四、 渐进探知与决策分支引擎

### 4.1 两维决策矩阵（意向强度 × 画像完备度）
画像完备度得分：$\text{Completeness} = \sum (\text{核心字段权重}) \in [0.0, 1.0]$

| 场景划分 | 画像充分 ($\ge 0.7$) | 画像不足 ($< 0.7$) 时的决策 |
| :--- | :--- | :--- |
| **高意向咨询 (询价/方案)** | 深度个性化方案生成 | **【价值置换混合探针】**：基准解答 + EVOI 最优闭合探针 |
| **低意向/常规技术咨询** | 针对性技术解答 | **【标准通用模板】**：专业作答，绝不查户口 |
| **Follow-up 延时跟进** | 结合痛点推针对性案例 | **【行业通用标杆案例】**：退守大行业通用价值，严禁造痛点 |

### 4.2 价值置换修辞对齐（消解审讯感）
探针生成必须遵循三段式修辞拓扑：
$$\text{通用解法确认} \longrightarrow \text{引入行业差异化进阶方案} \longrightarrow \text{二选一闭合式分流}$$
*范例：“关于高并发诉求，系统原生支持 HPA。金融级场景多采用全专有云，敏捷团队多用混合托管。不知贵司更贴近哪种？以便为您定向调优压测方案。”*

### 4.3 基于信息期望价值 (EVOI) 的探针数学排序模型
当多个画像特征同时缺失时，通过确定性算法计算最优单个探针：
$$S(Probe_i) = I(Y; D_i) \times \mathcal{P}(\text{Answer} \mid D_i, \text{Stage}) \times \frac{1}{\text{CognitiveCost}(D_i)} \times \prod \text{Dependency}(D_i, \text{State})$$
- **成单信息增益 $I(Y; D_i)$**：根据数万历史单转化后验，计算消除的成单不确定性；
- **回答响应概率 $\mathcal{P}$**：早期轮次客户对“预算”拒答率超 80%，对“技术二选一”回复率达 68%；
- **认知阻抗惩罚 $\text{Cost}$**：预算阻抗设为 3.5，部署形态设为 1.0；
- **DAG 依赖掩码**：技术适配未确认前，商务探针的依赖掩码置 0 强制剪枝。

# 五、 全链路可观测、延时调度与持续进化闭环

### 5.1 延时跟进“绝对零撞车”三道防线
1. **入站无锁 CAS 抢占式注销**：Webhook 收到邮件在 1ms 内执行：
   ```sql
   UPDATE thread_follow_up SET status = 'INVALIDATED'
   WHERE thread_id = :id AND status IN ('SCHEDULED', 'GENERATING');
   ```
2. **定时器启动双检锁**：Worker 唤醒后获取 Redis Redlock 排他锁，检查底表状态若非 `SCHEDULED` 则立即销毁任务；
3. **出站前 1ms 原子条件终审围栏**：调用 SMTP 前最后一毫秒执行带行锁更新：
   ```sql
   UPDATE thread_follow_up SET status = 'SENT'
   WHERE thread_id = :id AND status = 'GENERATING' AND last_inbound_time < :gen_start_time;
   ```
   若受影响行数为 0，说明生成期间客户回信，立即阻断出站。

### 5.2 三维生产监控看板指标体系与 SLA
| 维度 | 监控指标 | 告警阈值 | 生产目标 SLA |
| :--- | :--- | :--- | :--- |
| **质量安全** | 0 修改直发率 (Acceptance Rate) | $< 60\%$ (持续 2h) | $\ge 85\%$ |
| **质量安全** | Levenshtein 编辑距离中位数 | $> 0.35$ | $\le 0.10$ |
| **质量安全** | 跟进撞车事故数 (Collision Violations) | $> 0$ (P0 级) | **绝对 0 起** |
| **业务效能** | Follow-up 唤醒转化率 | $< 15\%$ | $\ge 30\%$ |
| **系统性能** | 端到端生成时延 (P95 Latency) | $> 5.0\text{s}$ | $\le 2.5\text{s}$ |

### 5.3 不可变快照包与时间旅行 (Time-travel Replay) 沙箱回放
每次执行持久化不可变快照包至 S3：
```json
{
  "trace_id": "tr-20260904-00129",
  "raw_email_mime": "s3://mail-dumps/raw/2026/09/msg-88912.eml",
  "macro_state": "Value_Validation",
  "intents": ["inquiry_delivery_time", "pricing_tier"],
  "prompt_git_hash": "a4f891b",
  "rag_context_snapshot": [{"doc_id": "sop.pdf", "chunk_id": 142, "content": "..."}],
  "model_config": {"model": "gpt-4o-2024-11-20", "seed": 42}
}
```
**单变量置换测试（A/B Controlled Swap）**：在隔离沙箱中单变量置换模型版本、Prompt 或 RAG 切片快照，30 分钟内精准定位根因。

# 六、 场景扩展性与技术栈清单

### 6.1 场景二（销售自动化）与场景三（项目协同）无缝扩展规范
得益于基座的分层解耦，后续接入场景 2 和场景 3 时，**基座代码变动率 $< 10\%$**：
- **场景 2（销售线索评分与客户旅程）**：
  - 复用 `customer_profile` 存储结构与 `BaseConnector`；
  - 接入 CRM（HubSpot/Salesforce）Webhook，编排 `LeadScoringGraph` 节点。
- **场景 3（项目任务派发与瓶颈预测）**：
  - 复用 `StateGraph` 调度器与时间旅行排错框架；
  - 接入 Jira/Linear MCP，编排 `TaskDispatchGraph` 与交付滞后预警节点。
