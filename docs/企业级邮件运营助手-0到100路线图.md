# 企业级 AI 邮件运营助手：从 0 到 100 的完整落地路线图

> 版本：v0.1 设计基线
> 适用对象：自动化服务商、自由职业者、企业 AI 工程团队
> 首期目标：Gmail 邮件回复 + 飞书审批 + 知识库检索 + 自动跟进 + 最小客户画像
> 部署原则：每个客户独立 Docker Compose 实例
> 安全原则：所有外发邮件默认必须经过人工审批

本文是项目从需求确认、工程基线、核心能力、可靠性、试点到生产化的可执行路线图。每个阶段都有：交付物、技术选择、可能情况、评测方法、通过门槛、失败处理和下一步优化方式。

---

## 1. 最终目标和边界

### 1.1 产品目标

构建一个面向自动化服务商的开源、可替换、可审计邮件运营底座：

```text
Gmail 入站
  → 事件验证与幂等
  → 邮件解析和意图识别
  → 销售阶段判断
  → 简单邮件走普通 LangGraph 节点
  → 复杂邮件进入 Reply DeepAgent 子图
  → 知识库检索和证据绑定
  → 回复草稿与事实校验
  → 飞书审批
  → Gmail 幂等发送
  → 跟进计划
  → 新邮件/退订自动取消跟进
  → 异步更新最小客户画像
```

### 1.2 一期实现范围

- Gmail/Google Workspace OAuth、Pub/Sub 接入和发送
- FastAPI 控制面
- 外层 LangGraph 业务图
- 内嵌 Reply DeepAgent 子图
- 普通回复路径和复杂邮件路径
- 销售阶段：破冰初筛、资格审查、价值主张、异议处理、促成跟进
- 本地 Markdown/PDF/DOCX 知识库
- PostgreSQL + pgvector、Redis、MinIO/S3 兼容对象存储
- 飞书交互卡片审批
- 跟进调度、取消和防撞车
- 证据型最小客户画像 Agent
- 日志、指标、快照、回放、故障恢复

### 1.3 明确不做

- 无审批自动直发
- CRM 深度同步
- 营销活动自动化
- 项目管理平台集成
- 每客户单独微调模型
- Kubernetes 平台化治理
- 任意 Shell 或主机文件访问
- 让模型直接修改生产画像、配置或审批状态

## 2. 总体架构

```text
                 ┌─────────────────────┐
                 │     Gmail / 飞书     │
                 └──────────┬──────────┘
                            │ HTTPS
                 ┌──────────▼──────────┐
                 │       FastAPI        │
                 │ 验签 / 鉴权 / 幂等 / API │
                 └──────────┬──────────┘
                            │ Inbox / Outbox / Queue
                 ┌──────────▼──────────┐
                 │       Worker         │
                 │ 外层业务 LangGraph    │
                 └──────────┬──────────┘
                            │
        ┌───────────────────▼───────────────────┐
        │             Reply DeepAgent            │
        │ Skills / Tools / 子 Agent / 规划与检索 │
        └───────────────────┬───────────────────┘
                            │ 结构化结果
                 ┌──────────▼──────────┐
                 │ 事实校验 / 审批 / 发送 │
                 └──────────┬──────────┘
                            │
        ┌───────────────────▼───────────────────┐
        │ PostgreSQL | Redis | pgvector | MinIO │
        └───────────────────────────────────────┘
```

职责边界：

| 组件 | 负责 | 不负责 |
|---|---|---|
| FastAPI | Webhook、OAuth、鉴权、幂等、状态查询、暂停/恢复 | LLM 长任务、回复生成 |
| 外层 LangGraph | 业务状态、Checkpoint、审批中断、重试、发送前检查 | 自由规划、直接管理 HTTP |
| DeepAgent | 复杂任务规划、Skills、只读工具、回复方案 | Gmail 发送、正式画像写入 |
| Tools | 受限读取、检索、计算和候选结果 | 任意 SQL、任意文件、绕过审批 |
| PostgreSQL | 业务事实、Checkpoint、Outbox、审计 | 高速短锁 |
| Redis | 队列、锁、限流、短期协调 | 唯一事实源 |
| MinIO/S3 | 原始 EML、附件、快照、大文本 | 业务状态判断 |

## 3. 推荐技术选型

### 3.1 默认选型

| 领域 | 推荐 | 选择理由 | 替代方案 |
|---|---|---|---|
| 语言 | Python 3.12 | LangChain/LangGraph/DeepAgent 生态完整 | Python 3.11 |
| API | FastAPI + Pydantic v2 | 异步 Webhook、类型契约、自动 OpenAPI | Starlette |
| 工作流 | LangGraph | Checkpoint、interrupt、resume、子图 | Temporal（后期可评估） |
| Agent Harness | `deepagents` | Skills、SubAgent、Memory、HITL 扩展 | `langchain.create_agent` |
| ORM/迁移 | SQLAlchemy 2 + Alembic | 事务和迁移成熟 | SQLModel |
| 主数据库 | PostgreSQL 16 | 业务数据、Checkpoint、审计统一 | PostgreSQL 15 |
| 向量检索 | pgvector | 独立部署简单，和业务元数据同库 | Qdrant |
| 队列 | Redis Streams + 独立 Worker | Compose 简洁、可实现重试和消费组 | RabbitMQ/Celery |
| 对象存储 | MinIO（S3 API） | 本地和云端 API 一致 | AWS S3 |
| Gmail | Gmail API + Pub/Sub | 原生 Thread、OAuth、事件通知 | IMAP/SMTP |
| 审批 | 飞书开放平台卡片 | 与当前目标团队匹配 | Slack Block Kit |
| 可观测 | OpenTelemetry + Prometheus + Grafana + Loki | Trace、指标、日志统一 | LangSmith + 云监控 |
| 测试 | pytest + pytest-asyncio + Testcontainers | 单元、集成、故障注入 | unittest |
| 密钥 | Docker secrets 或 Vault 兼容方案 | 避免密钥进入环境日志 | 云 KMS |

### 3.2 队列升级条件

Redis Streams 足够支持首期。出现以下情况时评估 RabbitMQ、Kafka 或 Temporal：

- 需要复杂优先级和跨队列路由
- 需要严格的任务调度可视化
- 需要跨服务长事务和补偿编排
- 单实例吞吐和恢复要求超过 Redis 运维边界

不要在一期因为“企业级”而过早引入所有中间件。

## 5. 阶段 0：需求、边界和验收基线（0–5）

### 5.1 工作内容

1. 冻结首期范围和不做清单。
2. 明确每客户独立部署、Gmail、飞书审批、本地知识库等约束。
3. 定义租户、客户、Thread、Run、Checkpoint、Approval、Follow-up 等核心实体。
4. 建立风险分类：普通、敏感、高风险、禁止自动化。
5. 建立 Golden Dataset 初版，至少覆盖 50–100 封脱敏邮件。
6. 写出验收标准和故障处理 Runbook。

### 5.2 可能情况和处理

| 情况 | 处理 |
|---|---|
| 客户要求加入 CRM | 记录为二期 Adapter，不改变一期主图 |
| 业务方要求自动直发 | 保持审批默认，先用影子模式评估 |
| 需求同时包含营销和项目管理 | 拆为后续子图，不扩张首期 |
| 真实邮件样本不足 | 使用脱敏模板和人工构造边界案例，并标注数据不足 |

### 5.3 Gate 0

- 有明确的一期范围和排除项
- 有数据分类和审批规则
- 有初版 Golden Dataset
- 每个核心流程都有成功、失败和人工兜底路径
- 关键指标有定义、数据源和负责人

## 6. 阶段 1：独立仓库和工程骨架（5–10）

### 6.1 工作内容

建议目录：

```text
src/ai_ops/
├── api/
├── domain/
├── graphs/
├── agents/
├── skills/
├── tools/
├── connectors/
├── knowledge/
├── memory/
├── application/
└── infrastructure/
```

建立：

- 独立 Git 仓库
- `pyproject.toml` 和锁文件
- `.env.example`，不包含真实密钥
- Docker Compose 和健康检查
- pytest、lint、type check、CI
- 配置分层：默认值、环境变量、租户配置、运行时策略

### 6.2 可能情况和处理

- 上层仓库存在大量脏改动：只在当前目录初始化，先确认目标路径，不移动上层文件。
- Windows 和 Linux 路径差异：所有容器内路径统一 POSIX，宿主路径通过 Compose 变量传入。
- 依赖版本漂移：锁定 LangGraph、DeepAgent、LangChain 和数据库驱动版本。
- 本地没有 Docker：提供纯 Python 单元测试，但集成 Gate 必须在 Docker 环境执行。

### 6.3 Gate 1

```text
docker compose config       # 配置可解析
docker compose up -d        # 服务可启动
GET /healthz                # 返回组件状态
pytest                      # 基础测试通过
```

禁止在日志中出现 API Key、OAuth Token 和数据库密码。

### 7.2 状态契约

```text

├── tenant_id
├── thread_id
├── inbound_message_ref
├── conversation_summary_ref
├── profile_snapshot_ref
```

```text

/memories/   → StoreBackend       长期画像和摘要
/artifacts/  → BlobStore          EML、附件、快照
```

生产环境不启用 `LocalShellBackend`，不向 Agent 提供 `execute`。

### 7.4 Gate 2

- 数据库迁移可重复执行
- 备份可以恢复到新数据库
- 租户负向隔离测试通过
- Checkpoint 不保存附件正文和密钥
- Store、Blob、业务表的命名空间一致

## 8. 阶段 3：Gmail 接入和事件可靠性（20–30）

### 8.1 实施步骤

1. 创建 Google Cloud 项目和 OAuth Consent Screen。
2. 配置最小 Scope：`gmail.readonly`、`gmail.send`；只有需要标记已读时才增加 `gmail.modify`。
3. 完成 OAuth 回调和加密 Token 存储。
4. 配置 Gmail `watch` 和 Google Cloud Pub/Sub。
5. FastAPI 接收通知后立即返回 `202`。
6. 使用 `history_id` 拉取真实邮件。
7. 以 `provider + provider_message_id` 做唯一幂等。
8. 写入 Inbox 和 Outbox，再投递 Worker。

### 8.2 可能情况

| 情况 | 处理 |
|---|---|
| Pub/Sub 重复通知 | 唯一键去重，返回已处理状态 |
| Gmail watch 过期 | Scheduler 定期续订，失效时重新建立 |
| history_id 太旧 | 回退到时间窗口同步，并记录补偿事件 |
| 邮件内容读取失败 | 任务重试，达到上限后人工队列 |
| OAuth 过期 | 刷新 Token，失败则暂停该租户并通知管理员 |

### 8.3 评测和 Gate 3

- 重复事件不重复建 Thread：100%
- 事件持久化后 FastAPI 返回：不等待 LLM
- Gmail 失败时事件仍保存在 Inbox
- OAuth Token 不进入日志、Checkpoint 和 Prompt
- 正常邮件、附件邮件、HTML 邮件、空正文邮件均有处理结果

## 9. 阶段 4：外层 LangGraph 生命周期（30–40）

### 9.1 主图

```text
START
  → load_event
  → normalize_email
  → load_context
  → triage
  → route
      ├─ ignore
      ├─ manual_review
      ├─ simple_reply
      └─ deep_reply
  → fact_check
  → approval_interrupt
  → send_guard
  → send_email
  → schedule_followup
  → profile_outbox
  → END
```

### 9.2 恢复和并发

- PostgreSQL Checkpointer 保存每个 super-step。
- `thread_id` 和 `tenant_id` 共同决定隔离。
- 同一 Thread 使用队列分区和数据库锁串行处理。
- Checkpoint 更新使用版本校验，拒绝旧状态覆盖新状态。
- 审批中断通过 `interrupt/resume` 恢复。
- 外部副作用全部由幂等应用服务执行。

### 9.3 可能情况

- Worker 在节点中途崩溃：从最近 Checkpoint 恢复。
- 审批暂停数天：恢复时重新检查客户状态、知识版本和紧急停止开关。
- Graph 版本升级：旧任务继续用旧版本，新任务使用新版本；只有有 State Adapter 才迁移。
- 同一客户两个 Thread 同时更新画像：使用 Profile Delta、Outbox、CAS 和语义合并。

### 9.4 Gate 4

- 人工中断后可恢复
- 任一 Worker 重启后不丢任务
- 同一 Thread 并发测试不会产生状态覆盖
- 可使用 `run_id → checkpoint_id` 重放一次运行
- 未到达发送守卫时不会触发 Gmail API

## 10. 阶段 5：知识库和普通回复路径（40–50）

### 10.1 知识处理流程

```text
客户文档目录
  → 类型/病毒检查
  → 解析
  → 结构化分片
  → 元数据校验
  → 混合索引
  → 离线回归
  → 发布 active 版本
```

文档必须包含：标题、产品、地区、语言、有效期、权威级别、可见租户、版本号和内容哈希。

### 10.2 召回策略

- 结构感知分片，避免切断价格和限制条件
- 关键词 + 向量混合召回
- 按租户、产品、地区和有效期过滤
- 对价格、SLA、交期、部署能力单独加权
- 重排并过滤重复、过期和低质量 OCR 片段
- 最终声明强制绑定 `evidence_ref`

### 10.3 普通回复路径

适合单意图、低风险、一次检索即可回答的邮件。输出：

```text
intent
sales_stage
claims
evidence_refs
draft_subject
draft_body
risk_flags
```

### 10.4 可能情况

- 无召回结果：回复需要人工确认，不允许常识补齐。
- 同一产品有多个有效版本：按 `knowledge_snapshot_id` 和生效日期选择。
- 知识更新正在进行：当前运行固定旧快照，新运行使用新版本。
- 文档被发现错误：撤销版本、影响分析、未发送草稿失效、已发送邮件进入人工补救。

### 10.5 Gate 5

- Golden Dataset 上证据精确率达到预设阈值
- 所有商业声明都能定位到文档片段
- 过期价目表不会被召回
- 知识版本切换不会造成单次运行前后混用
- 普通路径不需要调用 DeepAgent

## 11. 阶段 6：Reply DeepAgent 复杂路径（50–65）

### 11.1 触发策略

普通路径条件：

- 单一明确意图
- 低风险
- 一次检索足够
- 分类置信度初始目标不低于 `0.85`
- 无跨邮件推理和画像写入需求

DeepAgent 条件：

- 两个以上重要意图
- 砍价、竞品、定制化、复杂异议
- 需要两个以上工具
- 需要结合画像和多轮历史
- 分类置信度不足
- 需要制定跟进策略或生成画像候选补丁

投诉、法律、数据删除和重大安全事件直接人工。

### 11.2 DeepAgent 规划

采用受约束的 Plan-and-Execute + 局部 ReAct：

```text
结构化任务分析
  → 最多 4 步计划
  → 并行只读工具
  → 证据检查
  → 最多一次补检索
  → 回复合成
  → 返回结构化结果
```

限制：

- 最大计划步骤：4
- 最大工具轮次：6
- 最大自动纠错：1
- 总超时：按环境配置
- 重复工具指纹立即告警或熔断

### 11.3 专属 Tools

允许：

- `search_knowledge`
- `get_product_fact`
- `get_pricing_policy`
- `get_conversation_summary`
- `get_customer_profile`
- `classify_intents`
- `check_claim_risk`
- `propose_profile_delta`
- `create_reply_draft`

禁止：

- `send_gmail`
- `approve_email`
- `change_approval_status`
- `cancel_followup`
- `write_raw_customer_record`
- 任意 SQL
- Shell 和宿主机文件访问

### 11.4 画像 Agent

输出必须区分：

```text
FACT       明确表达且有原文证据，可进入候选画像
INFERENCE  多个证据支持，只能内部参考
HYPOTHESIS 推测，不得写入长期画像，也不能用于商业承诺
```

正式写入只能通过 Profile Delta、证据验证、版本校验和 Outbox。

### 11.5 可能情况

- 工具超时：只重试当前步骤。
- 工具返回冲突：记录冲突，重新检索一次或转人工。
- DeepAgent 循环：按工具指纹、结果哈希、无进展轮次和 Token 预算熔断。
- 规划完成但证据不足：进入人工，不生成“看似完整”的回复。
- 最终事实校验失败：允许一次带驳回原因的重规划，仍失败转人工。

### 11.6 Gate 6

- 多意图邮件能覆盖各个重要问题
- DeepAgent 无法调用禁止工具
- 复杂路径失败可恢复或转人工
- 循环调用可在预算内熔断
- DeepAgent 输出始终经过主图最终事实门禁
- 不展示或存储隐藏思维链，只保存计划摘要和工具事件

---

## 12. 阶段 7：飞书审批和安全发送（65–75）

### 12.1 审批状态机

```text
GENERATING
  → FACT_CHECKED
  → PENDING_APPROVAL
      ├─ APPROVED
      ├─ EDITED
      ├─ REJECTED
      └─ ESCALATED
  → SEND_GUARD
  → SENDING
  → SENT
```

所有首封回复和跟进邮件都进入 `PENDING_APPROVAL`。

### 12.2 发送前四重检查

1. 审批状态仍有效。
2. 目标 Thread 没有新入站邮件。
3. 租户、客户和 Thread 没有暂停或紧急停止。
4. `idempotency_key` 未成功发送过。

Gmail 发送超时不能盲目重试，必须先查询 Sent、Thread 和 History；状态不确定时转人工。

### 12.3 Gate 7

- 未审批外发：0 次
- 编辑后发送内容与最终审批版本一致
- 审批暂停和恢复可用
- 发送超时不会重复发信
- 飞书重复回调不重复恢复 Graph

## 13. 阶段 8：跟进和最小客户画像（75–85）

### 13.1 跟进状态

```text
SCHEDULED
  → GENERATING
  → PENDING_APPROVAL
  → SENT
```

任何新入站邮件、退订、负面投诉和人工暂停都会将活动计划标记为 `INVALIDATED`。

### 13.2 防撞车机制

1. 入站事件极速失效旧计划。
2. 调度器启动时重新读取计划状态。
3. 生成前获取 Thread 锁。
4. 发送前使用数据库行锁和条件更新。
5. 只有期间没有新邮件且幂等键未成功，才允许调用 Gmail。

### 13.3 最小画像字段

- 公司
- 联系人角色（只有明确证据才写）
- 已确认需求
- 明确表达的偏好
- 异议
- 销售阶段信号
- 来源邮件、证据片段、置信度和版本

### 13.4 Gate 8

- 新邮件到达后旧跟进必定失效
- 同一 Thread 同时只有一个活动计划
- 跟进撞车率：0
- 画像事实全部可追溯
- A/B Thread 并发画像更新不会丢失事实

## 14. 阶段 9：安全、可靠性、观测和评测（85–95）

### 14.1 安全验收

- 租户交叉读取负向测试全部失败
- OAuth Token、API Key 不出现在日志、快照和 Prompt
- Prompt Injection 不能改变工具权限

- Gmail 超时和重复回调

- PostgreSQL 短暂不可用
- Redis 重启
- Worker 中途崩溃
- Checkpoint 写入失败
- 对象存储读取失败
- 知识版本切换
- 发送结果不确定

#### Agent 工程质量

## 16. 指标不达标时如何优化

优化必须从指标定位到组件，不允许只改 Prompt。

| 指标异常 | 首先检查 | 典型优化 |
|---|---|---|
| 意图 F1 低 | 标签定义、邮件切分、分类 Prompt | 重做 Schema、增加边界样本、校准路由阈值 |
| 阶段判断抖动 | 阶段定义、历史窗口、状态锁 | 增加滞后规则、阶段转移约束、人工标注 |
| Evidence Precision 低 | 文档元数据、分片、重排 | 过滤过期文档、结构化分片、混合召回 |
| Evidence Recall 低 | 查询改写、关键词覆盖 | 增加别名词、行业词典、查询扩展 |
| Unsupported Claim 上升 | 生成约束、证据门禁 | 强制 Claim-Evidence Schema、降低自由生成权限 |
| 人工修改率高 | 语气、漏答、事实或阶段 | Diff 聚类，分别修 Prompt、Skill、知识或路由 |
| DeepAgent 进入率过高 | 复杂度路由 | 增强普通路径，增加缓存和低成本模型 |
| DeepAgent 循环率高 | 工具描述、停止条件、结果格式 | 工具指纹熔断、最大轮次、结构化摘要 |
| P95 延迟高 | LLM、RAG、队列、锁 | 并行只读工具、上下文裁剪、缓存、限流 |
| Token 成本高 | Prompt、历史、重复工具 | 摘要、Top-K 限制、结果压缩、模型分层 |
| 跟进回复率低 | 跟进间隔、话术、客户阶段 | 稳定 A/B，按阶段和行业调整策略 |
| 撞车风险上升 | 失效时序、锁、发送守卫 | 强化原子条件更新，默认暂停外发 |
| 画像冲突多 | 来源优先级、CAS、合并规则 | 事件顺序、语义合并、人工确认 |

### 16.1 优化闭环

```text
线上事件
  → 脱敏快照
  → 指标异常定位
  → Bad Case 分类
  → 离线回放
  → 只改一个变量
  → Golden Dataset 回归
  → 影子流量
  → 灰度发布
  → 观察窗口
  → 保留或回滚
```

每次变更必须记录：原因、假设、修改组件、评测前后、成本变化和回滚方式。

## 18. 下一步执行顺序

在开始写业务代码前，按以下顺序执行：

1. 确认本文路线图和一期验收门槛。
2. 将路线图拆成设计规格和实现计划。
3. 在当前目录初始化独立 Git 仓库。
4. 创建工程骨架、依赖锁定和 Docker Compose。
5. 先实现数据库、Inbox/Outbox 和幂等，再接入 Agent。
6. 先完成普通回复路径，再接入 DeepAgent。
7. 先完成飞书审批和发送守卫，再开发跟进自动化。
8. 使用固定 Golden Dataset 和故障注入推进每个 Gate。
9. 影子运行和小租户试点后，再扩大范围。

路线图的核心原则是：先建立可靠的业务闭环，再增加智能复杂度；先把证据、权限、版本和恢复做实，再优化模型效果和自动化比例。
