## 记录状态

以下 ADR 是一期基础架构的提案，状态统一为 `Proposed — pending architecture/security/operations review`。它们约束后续实现方向，但不表示对应组件已经部署或具备生产能力。

## ADR 模板

每条 ADR 都必须包含以下字段：

- **Status**：当前评审/生效状态和责任人
- **Context**：需要解决的业务、可靠性或安全问题
- **Decision**：选择的架构和边界
- **Alternatives**：考虑过但未采用的方案及原因
- **Consequences**：对开发、运行和用户的影响
- **Costs**：基础设施、开发、运维和学习成本
- **Risks**：失败模式、残余风险和监控点
- **Rollback/Migration**：如何暂停、回退、恢复和迁移
- **Acceptance Evidence**：实施前后必须收集的证据

## ADR-001：FastAPI 作为控制面

- **Status**：`Proposed — pending architecture/security/operations review`
- **Context**：需要提供状态查询、审批命令、暂停/恢复、人工队列和健康检查等可鉴权入口，同时避免 HTTP 请求承载长时间模型或外部连接器任务。
- **Decision**：使用 FastAPI 作为无状态控制面；API 只负责认证授权、输入校验、任务启动、状态查询、审批命令和审计关联。长任务交给 Workflow/Worker，所有资源请求携带 tenant、Thread 和 Run 范围。
- **Alternatives**：仅用脚本/CLI 不利于业务接入；把生成和发送全部放在同步 API 中会导致超时、重复副作用和无法恢复；使用重型全栈框架会增加不必要的运行时边界。
- **Consequences**：控制面易横向扩展，调用契约清晰；需要额外设计异步任务查询、认证、错误码和幂等接口。
- **Costs**：增加 API Schema、鉴权中间件、请求追踪和部署进程；团队需要维护 API 版本。
- **Risks**：越权查询、错误消息泄露存在性、同步接口重复提交；以资源级授权、统一 Request ID、超时和幂等键控制。
- **Rollback/Migration**：先关闭写操作和外发命令，保留只读状态查询；API 版本向后兼容，旧客户端迁移到新版本前保留旧 Schema Adapter。
- **Acceptance Evidence**：未授权、跨租户、重复审批、暂停/恢复、超时和错误码契约测试；每个状态查询可关联 Trace 与 Audit。

## ADR-002：LangGraph 作为外层业务状态机

- **Status**：`Proposed — pending architecture/security/operations review`
- **Context**：邮件处理跨越入站、Triage、知识读取、草稿、审批、发送、跟进和画像候选，需要可暂停、可恢复、可审计的状态转换，而不是一次性函数调用。
- **Decision**：外层使用 LangGraph 编排业务状态；Graph 负责节点顺序、路由、interrupt/resume、Thread/Run 边界和最终门禁调用。短期状态与长期画像分离，瞬态上下文不沿轮次无界累积。
- **Alternatives**：手写 if/else 状态机难以统一 Checkpoint 和恢复；仅用消息队列会把业务状态分散在消费者中；让 LLM 自由决定下一步无法证明权限和终态。
- **Consequences**：状态转换可观察、可回放并支持人工中断；需要严格定义 State Schema、版本和 Checkpoint 膨胀策略。
- **Costs**：引入 LangGraph 学习、Checkpoint 存储、Graph 版本测试和状态迁移成本。
- **Risks**：错误 Reducer 累积敏感数据，旧 Graph 恢复时发生版本漂移，并发 Run 覆盖状态；以 Thread 锁、版本校验、快照和状态适配器控制。
- **Rollback/Migration**：暂停新 Run，使用兼容旧 Graph 版本恢复挂起 Run；迁移采用 expand → backfill → switch → contract，无法迁移时进入人工队列。
- **Acceptance Evidence**：中断/恢复、进程重启、旧新版本混跑、Thread 并发和状态大小测试；每个终态有 Graph 与数据库一致性证据。

## ADR-003：DeepAgent 作为 `CompiledStateGraph` 子图

- **Status**：`Proposed — pending architecture/security/operations review`
- **Context**：复杂异议、多意图邮件和需要多步证据整理的任务需要更强的规划能力，但生成、审批和发送仍必须由受控主图决定。
- **Decision**：将 DeepAgent 编译为受限 `CompiledStateGraph` 子图，由外层 Graph 根据任务风险和复杂度路由进入；子图只返回结构化草稿、证据引用和轨迹摘要，工具使用 Allowlist、循环次数、Token 和总时间均有预算。
- **Alternatives**：远程 Async SubAgent 会引入跨服务一致性和权限传播成本，留作未来扩展；让 DeepAgent 直接接收 HTTP 或调用发信工具会破坏主图控制；完全不用子图会牺牲复杂任务质量。
- **Consequences**：复杂任务有独立预算和可观测边界，外层仍拥有不可逆动作；需要定义父子状态映射、错误传播和子图版本。
- **Costs**：增加子图开发、轨迹记录、预算控制和回归样本；复杂任务的模型和计算成本更高。
- **Risks**：工具循环、Prompt Injection、上下文泄露和深层错误被误当作事实；Reader/Arbiter/Writer 分权、证据门禁和超预算熔断控制。
- **Rollback/Migration**：关闭增强路由开关，所有任务退回普通草稿或人工队列；子图版本独立发布，旧 Run 使用其原版本或经测试的 State Adapter。
- **Acceptance Evidence**：复杂任务路由准确性、工具 Allowlist、循环熔断、预算耗尽、注入样例和父图最终门禁测试。

## ADR-004：Worker/Queue 承担异步执行

- **Status**：`Proposed — pending architecture/security/operations review`
- **Context**：知识检索、模型生成、飞书恢复、Gmail 发送、跟进调度和画像候选都可能超过 API 请求生命周期，需要重试、削峰和进程恢复。
- **Decision**：API 只创建/查询 Run；Worker 处理生成、发送、画像和跟进任务，队列保存可恢复任务，任务包含幂等键、版本、租户/Thread 范围和预算。不同负载使用独立队列或并发配额，失败进入 DLQ。
- **Alternatives**：API 内同步执行会被网络和模型延迟拖垮；单一无界后台线程无法在进程重启后恢复；只用 Redis 短期锁无法承担业务事实。
- **Consequences**：任务可重试、暂停和恢复；系统需要队列可见性、租户公平性、Worker 健康、DLQ 管理和任务取消协议。
- **Costs**：增加队列、Worker 进程、监控、部署和运维成本；每个任务需要持久化状态。
- **Risks**：重复消费、毒消息、饥饿和无限重试；由数据库幂等约束、退避、预算、租户配额和 DLQ 控制。
- **Rollback/Migration**：暂停消费和外发，保留 Inbox/Checkpoint/Outbox；恢复后按版本和幂等键继续，旧任务不能隐式切换到不兼容的新 Graph。
- **Acceptance Evidence**：进程重启、重复消费、重试上限、DLQ、暂停/恢复、租户公平性和依赖故障注入测试。

## ADR-005：PostgreSQL、Redis、MinIO 分工

- **Status**：`Proposed — pending architecture/security/operations review`
- **Context**：系统同时需要保存可查询的业务事实、短期并发/队列状态以及大邮件、附件和不可变快照，混在同一存储会造成膨胀和恢复边界不清。
- **Decision**：PostgreSQL 保存租户、Inbox、Run、审批、Outbox、跟进、画像版本和 Audit 等业务事实；Redis 只保存短期队列、锁、限流和唤醒信号；MinIO 保存原始 MIME、附件和快照引用。Graph/Checkpoint 只存精简状态和 Blob URI。
- **Alternatives**：全部放 PostgreSQL 会造成大对象和 WAL 压力；全部放 Redis 不具备可靠业务事实；直接把附件放进 Graph 会放大 Checkpoint 并泄露更多上下文。
- **Consequences**：各存储职责清晰，便于备份和权限隔离；需要处理跨存储引用一致性、对象版本和恢复顺序。
- **Costs**：维护三类基础设施、连接池、备份策略、健康检查和数据生命周期；对象存储需要额外的版本与 GC 管理。
- **Risks**：引用悬空、Redis 丢失短期信号、对象权限过宽；Outbox/状态在 PostgreSQL，Redis 可重建，Blob 使用版本化 URI、加密和租户前缀。
- **Rollback/Migration**：先阻断依赖 Blob 的处理，保留数据库引用；恢复顺序为 PostgreSQL → MinIO → Redis 重建，不能用 Redis 是否存在来判断业务事实。
- **Acceptance Evidence**：数据库/对象/缓存故障演练、引用完整性、Checkpoint 大小、租户前缀权限和恢复验证。

## ADR-006：Gmail、飞书和 LLM Adapter 隔离

- **Status**：`Proposed — pending architecture/security/operations review`
- **Context**：外部供应商有不同的认证、错误、限流和副作用语义；业务 Graph 不应绑定某一家 SDK，也不应在测试中触发真实发送。
- **Decision**：定义 Gmail、飞书审批和 LLM 的最小领域接口，业务层只调用 Adapter；Mock/Real Adapter 可配置切换，外部错误映射到统一领域错误码，发送 Adapter 必须支持稳定 Message-ID、幂等查询和 unknown 结果。
- **Alternatives**：在节点中直接调用供应商 SDK 会让权限、重试和测试散落；只实现 Mock 会掩盖真实协议差异；把全部供应商封装成一个大 Adapter 会模糊权限边界。
- **Consequences**：连接器可替换、可契约测试、可在 Demo 中证明零真实副作用；需要维护契约版本、错误映射和供应商差异文档。
- **Costs**：编写接口、Mock、Contract Test 和 Provider 映射；真实供应商变更需要适配器维护。
- **Risks**：Adapter 错误映射导致重复发送或错误降级，权限 Scope 过宽；以最小 Scope、稳定幂等键、超时分类和 Provider 监控控制。
- **Rollback/Migration**：禁用 Real Adapter，切 Mock/只读/人工模式；新供应商先通过契约测试和影子验证，再按 Adapter 版本切换。
- **Acceptance Evidence**：Mock/Real 契约测试、权限失败、限流、超时、重复调用、发送 unknown 和回调重放测试。

## ADR-007：不可逆动作采用确定性最终门禁

- **Status**：`Proposed — pending architecture/security/operations review`
- **Context**：外发邮件、退订抑制、跟进调度、画像写入和高风险业务动作可能产生不可逆后果，模型判断无法单独证明权限、版本、证据和审批。
- **Decision**：在每次外部副作用前由确定性 Policy/Arbiter 最终校验租户与 Thread、操作者权限、任务风险、证据、草稿 hash、审批结果、策略版本、暂停控制和幂等状态；任一项不满足即阻断或转人工。
- **Alternatives**：只在 Prompt 中提醒模型会被注入和生成错误绕过；只在 API 入口校验会被队列重试和版本变化绕过；只依赖人工界面不能覆盖 Worker 和补偿路径。
- **Consequences**：发送安全性和审计性提高，正常路径多一次校验且需要明确状态机；策略规则必须版本化并可解释。
- **Costs**：开发 Policy Engine、权限查询、版本校验、锁和审计；发送延迟增加有限的确定性检查时间。
- **Risks**：规则漏项、检查与执行非原子、配置漂移；使用数据库条件更新/行锁、规则回归、配置快照和 P0 告警控制。
- **Rollback/Migration**：发现门禁异常时全局暂停外发，保留任务和证据；规则升级使用向后兼容版本，历史 Run 继续使用原策略或显式迁移。
- **Acceptance Evidence**：未审批、旧 hash、越权、无证据、暂停、重复调用、撞车和未知发送状态全部被阻断的负向测试。

## ADR-008：数据最小化与脱敏默认开启

- **Status**：`Proposed — pending architecture/security/operations review`
- **Context**：邮件正文、画像、合同、OAuth Token 和附件含有不同敏感级别；无边界地复制到 Prompt、日志、Trace 或 Checkpoint 会扩大泄露面。
- **Decision**：按 Public/Internal/Confidential/Restricted 分级，在进入 Prompt、日志、Trace、Checkpoint、Outbox 和快照前执行字段级最小化与脱敏；Restricted 数据只进入 Docker secrets 或 KMS 兼容存储。Break-glass 限时、最小字段并审计。
- **Alternatives**：保存完整原文方便排错但违反最小化；只靠人工提醒不可稳定执行；把所有数据都加密但不做访问控制无法降低业务越权风险。
- **Consequences**：调试需要引用、摘要和受控恢复，部分分析能力受限；数据保留、访问和删除责任更清晰。
- **Costs**：分类目录、脱敏规则、密钥管理、扫描和审计建设成本；误报需要人工复核。
- **Risks**：脱敏漏检、错误恢复泄露、敏感字段进入指标标签；使用负向测试、字段 allowlist、默认拒绝和定期轮换控制。
- **Rollback/Migration**：脱敏服务异常时阻断外发/LLM 请求，退回人工/只读；已有数据按新分类补标，不能为了恢复排错而放开全量日志。
- **Acceptance Evidence**：Token/PII/合同/附件扫描、Prompt 和日志负向测试、Break-glass 审计、密钥轮换和数据删除演练。

## 跨组件边界

```text
Inbound Adapter 只接收和标准化；Workflow 负责状态转换和路由。
Knowledge/Profile 只提供租户与 Thread 范围内的受限读取；审批 UI 只提供人工决定，不持有业务事实。
Outbox/Adapter 负责幂等副作用；Audit 记录不可变事件。
任何组件都不能同时拥有“生成任意内容”和“绕过最终发送门禁”的权限。
```

工作流、任务契约、Adapter 和数据库 Schema 分开版本化。回滚先暂停外发并保留 Inbox、Checkpoint、Outbox 和审计证据，再切换到兼容旧版本或人工队列；不得删除状态、重放未知发送或直接改写历史审计。
